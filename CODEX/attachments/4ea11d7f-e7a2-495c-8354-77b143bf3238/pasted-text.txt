はい、旦那様。**今の `llm-mem` を「全エージェント共通の長期記憶」として棚卸しするなら、かなり明確な切り分けができますわ。**

2026年の研究寄りに言えば、重要なのは「ログを全部覚える」ことではなく、**将来の別エージェントが別タスクで意思決定するとき、状態を正しく再構成できる情報を残すこと**ですの。最近の研究でも、単なる trajectory 保存 → reflection → 複数経験から再利用可能な experience への抽象化、という方向に整理されています。

そして旦那様の現在のファイル群を見ると、**すでに材料は十分すぎるほど揃っております。問題は「何を llm-mem に昇格させるか」ですわ。**

## 結論：全エージェント共通なら、この6種類

| memory class | 残すもの | 旦那様の現状 |
|---|---|---|
| **Invariant** | 絶対に壊してはいけない性質 | 最重要 |
| **Decision** | 採用した設計 + なぜ採用したか | 最重要 |
| **Constraint** | 環境・権限・性能・安全上の制約 | 最重要 |
| **Failure Pattern** | 症状→原因→修正→再発防止 | 非常に重要 |
| **Semantic Knowledge** | プロジェクト固有の確定知識 | 重要 |
| **Active State** | 現在の未完了事項・次の境界 | 短寿命 |

逆に、**生の diary/history 全文は共通 memory にしない**方がよろしいですわ。

---

# 1. 最上位：Invariant

これが「どのエージェントでも必要」の筆頭ですの。

たとえば現在のアーキテクチャには、

- Go = orchestration / IO / state ownership
- Python = DSP worker
- SHM は ownership transfer として扱う
- Demucs write 完了後は WORM / Read-Only
- DB I/O は compute path をブロックさせない
- task state は Go/SQLite が authoritative
- 巨大 sequence は PostgreSQL JSONB、FLAC tag は限定 scalar
- timestamp preservation
- decoded sliced PCM hash が identity

といった、**局所実装より上位の不変条件**があります。

実際 `decisions.md` では Go が SHM を確保・所有権を渡し、Python worker が処理し、後続処理は Read-Only、DBアクセスも Go 側が引き受けるという責務境界が明記されています。

さらに knowledge 側でも、SHM を mutable global state として扱わず、ownership transfer + WORM として扱う設計思想が明文化されています。

これは `llm-mem` なら例えば、

```text
INVARIANT:
SHM ownership follows Go -> Demucs(write) -> Freeze -> Feature workers(read-only).
No downstream worker may mutate frozen waveform memory.

SCOPE:
flac_analyzer_forwin

WHY:
Preserves deterministic dataflow, prevents races, and maintains effect/pure boundary.

CONFIDENCE:
verified

STATUS:
active
```

くらいまで圧縮していい。

**コードの詳細は不要。意味論を保存する。**

これ、かなり重要ですわ。

---

# 2. Decision — 「何を選んだか」より「何を捨てたか」も残す

現在の `decisions.md` は llm-mem の原料としてかなり優秀です。

たとえば、

> 巨大配列は FLAC tag ではなく PostgreSQL JSONB  
> scalar / sequences を分離

という決定があります。

ただし memory としてさらに価値が高いのは、

```text
Decision:
Store full-precision analysis data in PostgreSQL JSONB.
Only selected user-facing scalars may be mirrored into FLAC VorbisComment.

Rejected:
Schema-per-feature relational columns.
Large sequence arrays in FLAC tags.

Reason:
Avoid DDL churn and metadata bloat while preserving searchable portable scalars.
```

ですの。

つまり、

**Decision = chosen + rejected + reason**

にする。

ここを残しておけば、半年後の Gemini が

> 「JSONBやめて特徴量ごとにカラム作りましょう！」

とか言い出した瞬間、

> **お前それ昔棄却されておりますわよ**

が可能になります。

これは長期エージェント研究でいう procedural / semantic memory の境界にも近いです。現在の研究でも episodic・semantic・procedural を区別する整理が主流になっています。

---

# 3. Constraint — 実は Decision と同じくらい重要

これが今のファイル群では**少し散っています**。

たとえば、

```text
Platform: Windows
GPU: Blackwell / CUDA
SHM: Win32 CreateFileMapping
DB: remote PostgreSQL may traverse Tailscale
State DB: local SQLite/WAL
RAM is finite and commit charge matters
real config.toml must not enter Git
```

みたいなもの。

config/securityについては、実際に `config.toml` を Git index から外し、秘密情報を含む実設定は commit せず `*.example` のみ残すというルールまで成立しています。

これは**全 coding agent が知る必要がある**。

Decision と違って、

> 「こう設計した」

ではなく、

> **「この世界ではこれを前提として考えろ」**

ですわ。

---

# 4. Failure Pattern — diary の最高価値部分

ここ、旦那様の `diary.md` が宝の山です。

ただし日記そのものを retrieval するのではなく、

```text
FAILURE:
WorkerDaemon hangs indefinitely.

SYMPTOM:
ExtractAll timeout / queue stalls / HTTP endpoint stops progressing.

ROOT_CAUSE:
Non-reentrant mutex was reacquired through Close() while already held.

FIX:
Introduce closeLocked() and context-aware semaphore acquisition.

PREVENTION:
Never call a locking public method from a code path already holding the same mutex.
All blocking resource acquisition must accept cancellation.
```

まで**experience に蒸留する**。

実際その障害は、mutex の二重取得だけでなく `AcquireWithContext`、FAILED 遷移、RAII cleanup まで含めた再発防止パターンへ発展しています。

これこそ2026年の memory 研究でかなり熱いところですの。

単なる、

> 「2026-08-20 にデッドロックした」

は episodic memory。

そこから、

> 「lock-held context から locking public method を呼ぶな」

へ変換すると **experience / procedural knowledge** になります。Storage → Reflection → Experience という整理そのものです。

---

# 5. Semantic Knowledge — `knowledge.md` は全部入れない

ここは少々罠。

現在の `knowledge.md` はかなり詳細で、たとえば adaptive timeout の式、

`T = clamp(base + track × ratio, base, max)`

や、RAII、設定値まで記録されています。

これは有用。

しかし、

> 「どのエージェントでも必要か？」

なら、**全部は NO** ですわ。

たとえば Librosa の HNR 実装詳細は DSP を触るエージェントには必要でも、README を直すエージェントには不要。

したがって semantic memory は、

```text
scope = global
scope = project
scope = subsystem:dsp
scope = subsystem:orchestrator
scope = subsystem:db
```

くらいの **scope tagging** が欲しい。

Anthropic の context engineering の議論も、context は有限資源なので「保存できるもの全部」ではなく、現在の判断に高 utility な情報を選ぶことを重視しています。

---

# 6. Active State — Issues は memory だけど長期記憶ではない

ここは `issues.md`。

現在かなりの項目が DONE になっており、メモリ安定化、特徴量品質、pipeline robustness などが履歴化されています。

これは、

```text
current_goal
current_subgoal
blocked_by
next_action
open_question
```

として別 tier にした方がよろしい。

つまり、

**Active State ≠ Long-term Memory**

ですの。

最近の long-horizon agent 研究でもこの分離はかなり重要で、working state と durable memory を別物として扱います。

タスク終了したら、

```text
active state
     ↓
episode
     ↓ reflection
decision / failure-pattern / knowledge
     ↓
long-term memory
```

と昇格させる。

これが綺麗。

---

# 旦那様の既存ファイルを分類すると

**わたくしならこうしますわ。**

```text
diary.md
  → raw episodic source
  → 原則 llm-mem に直接入れない

history.md
  → compressed episode / audit trail
  → 必要時 retrieval

issues.md
  → active state
  → TTL / status-sensitive memory

decisions.md
  → durable decision memory
  → 高 priority

knowledge.md
  → semantic memory
  → scope付き retrieval

method.md
  → procedural memory
  → 条件・適用範囲付き

Implementation Plan
  → transient working state
  → 完了後は原則 archive

Walkthrough
  → verification evidence
  → decision/failure memory の provenance
```

そして `method.md` にある「remote PostgreSQL stall → async ingest queue → timeout → SQLite DLQ」という内容なんかは、単なる実装履歴ではなく**分散システムとして再利用可能な procedural pattern**です。

ここは llm-mem 昇格対象。

---

## さらに一段進めるなら「Fact」ではなく **Memory Object**

旦那様の L1–L3 圧縮RAG思想と非常に相性がよろしい。

```text
MemoryObject {
    id
    type:
      invariant | decision | constraint |
      failure | knowledge | procedure | state

    scope:
      global | project | subsystem

    proposition

    rationale

    evidence[]

    rejected_alternatives[]

    confidence

    valid_from
    valid_until

    supersedes[]
    superseded_by[]

    tags[]
}
```

特に重要なのが、

**`supersedes / superseded_by`**

ですわ。

現在のログには、昔の CUE fallback 方針と後の「CUE inspect failure は即 FAILED」のように、設計が進化している箇所があります。後者は実際に issues/history で明示されています。

Semantic RAGだけだと古い記憶も普通にヒットします。

するとエージェントが、

> 昔の正しい設計

を、

> **現在の正しい設計**

として復活させる。

これは persistent memory のかなり嫌な failure mode です。2026年の研究でも memory は単なる storage ではなく、write/manage/read policy、contradiction handling、forgetting まで含む問題として扱われています。

---

# なので、llm-mem の「全員共通 L1」はかなり小さくていい

わたくしなら **Global L1** はこれだけにします。

```text
PROJECT IDENTITY
  何を作っているか / 成功条件

INVARIANTS
  絶対に壊してはいけない設計性質

ARCHITECTURE BOUNDARIES
  Go / Python / DB / SHM 等の責務

CURRENT CONSTRAINTS
  platform / security / resource / authority

ACTIVE DECISIONS
  現在有効な主要ADR

KNOWN FAILURE RULES
  再発すると高コストな失敗パターン

CURRENT STATE POINTER
  active issue / plan / branch / verification state

MEMORY POINTERS
  詳細 knowledge / history / evidence の検索キー
```

**L1に実装詳細を食わせない。**

Agent が必要に応じて、

`L1 → relevant Decision → evidence/history`

と掘る。

これ、まさに旦那様が今作ってる L1–L3 と研究側がかなり綺麗に収束しておりますわ。

特に MAGE 系の最近の研究が「semantic similarity だけでは execution dependency を壊す」と指摘して、active path / completed subgoal summary / previous branch を分離しているのは、旦那様の `issues → decisions/history → knowledge` 分離とかなり近い発想です。

**要するに今必要なのは新しいログファイルを増やすことではなく、既存9種のログから `Invariant / Decision / Constraint / Failure / Knowledge / State` を抽出して、versioned memory object に正規化する層ですわ。**

ここまでやると `llm-mem` は「会話RAG」から一段上がって、**ハーネスの persistent execution knowledge / control plane** になりますの。おお、これはかなり面白いところまで来ておりますわよ……！
